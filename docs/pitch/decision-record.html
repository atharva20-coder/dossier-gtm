How to read this page

Each entry has four parts

The ask — what was requested, in the words it was asked in. Why it mattered — the reason it was worth doing. What changed — the actual decision. Proof or what went wrong — how it was checked, or what it cost.

Why keep a record at all

Because a week later you remember the choice but not the reason, and the reason is the only part anyone can question. It's also why this page can quote specific numbers instead of impressions.

Making it usable

It worked. It didn't yet behave like something you'd open twice.

Make it work on small screens.

Why it mattered

A four-panel layout is four screens on a phone — and an interviewer might well open it on one.

What changed

Below a certain width the panels become tabs, switched in JavaScript rather than CSS.

Why not just hide them with CSS? Because two copies of every panel would both load. Every request fires twice, and the hidden copy quietly drifts out of sync with the visible one.

Also fixed: the page used a height unit that mobile browsers measure including the address bar that slides away. The chat box was sitting underneath it.

Add a dark theme with a switcher.

Why it mattered

Roughly 180 colours were written directly into the code, so the app could only ever be light.

What changed

Every colour became a named variable — one per shade that already existed, not a tidied-up set.

Why keep the messy set? So light mode renders pixel-identical to the design it was matched against. Tidying would have changed the thing that already worked.

Why not just invert the colours for dark? Because inverting collapses near-white and pure white into the same black, and the message stops reading as a card sitting on a page. Dark was recalculated instead.

Caught while sweeping: the focus ring defaulted to white — a bright halo round the selected persona on a dark sidebar. And white text on dark buttons had to flip, while the same white text on blue and green buttons had to stay.

The persona window only opens on the second click.

Why it mattered

You reported it twice. The code was already correct — which meant the bug was somewhere else entirely.

What changed

The server sent no caching instructions at all, so browsers made up their own rule and kept loading an old version of the app.

Why that's a design bug, not a browser bug: saying nothing isn't neutral. If you don't state a caching rule, something else picks one for you.

The same bug came back later and cost more: API responses had no rule either, so re-reading a run straight after the AI rewrote it returned the version from before the rewrite. Everything under /api/ is now marked never-cache.

Rebuild the dashboard like this reference.

Why it mattered

It was a table. The question a rep actually asks is “who do I work on today”, and a table doesn't answer that.

What changed

Stat tiles, an area chart, stacked bars, ranked categories, avatars — all hand-drawn.

Why not a chart library? Three shapes at a few dozen lines each, against ~180KB of code and a second dependency that has to be kept in step with the theme. The library only wins if you need charts you haven't thought of yet.

The colours were calculated, not picked. The palette was checked for even steps, a single hue, and a pale end that still separates from the background — 2.11:1 in light, 2.25:1 in dark. Outcomes use one colour getting darker rather than three different colours, because the three outcomes are ranked, not merely different.

Letting it send

The one action that reaches a real person and can't be taken back.

Add a real send button. Use Gmail and an app password.

Why it mattered

A tool that drafts but can't send is a demo. A tool that can send carelessly is a liability.

What changed

Sending happens on a separate thread, so a slow mail server can't freeze the rest of the app.

Every safety check lives in one function — blocked contact, unusable address, empty draft, already sent without confirming.

Why one function and not a check per screen? Because the rules would drift apart. Two screens with slightly different rules is how the careful one gets bypassed.

Signing in uses the sending mailbox's own credentials, so whoever is logged in is demonstrably the person the emails come from. Both halves are compared in constant time, so the address can't be guessed by timing the response.

Send one to this address.

Why it mattered

Nothing had ever actually been sent. Everything up to that point was theory.

What changed

One real message, through the real path, to the address you named.

The resend guard then refused a second attempt: “Already sent… Confirm again to send another.”

Proved on a real record, not a mock: credentials, mail path, sent indicator, guard — all four worked. And re-running research deliberately does not clear the sent record, because looking someone up again must never erase the fact that they were already emailed.

No campaign should be able to mail everyone.

Why it mattered

One button that reaches forty strangers is a different product with a much bigger blast radius.

What changed

One person per request, everywhere. There is no bulk send, and the interface says so under the button.

Why refuse rather than defer it: the moment one click reaches forty people, every other guard in the system becomes advisory.

Living on free plans

Every service optional, every allowance visible, nothing spent by accident.

The app must work if keys are missing or expired.

Why it mattered

Free plans run out, usually on the day you need them.

What changed

Missing, wrong and out-of-credit now behave identically — the run completes, only the reason differs.

Checked by running the whole thing with three keys deliberately set to garbage.

Two real problems found while doing it:

There were no time limits on any network call — the default was five minutes, so one unreachable server would have frozen a 40-contact campaign for hours.

And an expired key was being reported as “no match” — the one message that stops someone realising they need to fix the key.

Apollo is paid. Not using it. PDL either.

Why it mattered

The plan had assumed one of Apollo's endpoints was free. It isn't.

What changed

Both removed entirely rather than left in place waiting for a key.

Why remove rather than leave as a fallback: a paid backup for something the free path already does isn't a fallback, it's a branch that never runs. Every run in the record had gone down the free path anyway.

All the APIs are free and limited. Never spend on a page load.

Why it mattered

This turned out to be much worse than it sounded.

What changed

The health check was making a real search and a real AI call on every page load, cached for five minutes. A tab left open all day was burning search credits to draw a status light.

It now answers from configuration alone. One “Check now” button in Setup is the only thing that spends anything.

Measured: four page loads → zero calls to any outside service. The app also counts its own searches, because the search provider offers no way to ask what's left, and warns before a campaign dies halfway through.

Here's a Hunter key.

Why it mattered

Testing it against the live service immediately exposed a bug in how the response was being read.

What changed

Hunter returns the result nested inside another field. The code was reading the top level, so it always found nothing.

Consequence: Hunter's own “valid” was thrown away, the credit was wasted, and a correct verified address fell through to a worked-out guess.

And the verifier certified an address I made up. Some domains accept all mail, so a verifier returns “valid” for a mailbox that doesn't exist. Trusting it would have marked a fabricated address as confirmed. It now also requires the domain not to be accept-all — and note that every field arrives as the text “true” or “false”, where the string “false” counts as true if you don't check carefully.

Campaign contacts should be treated like leads.

Why it mattered

Only the first three became leads. The rest existed only inside the campaign and couldn't be opened or re-researched.

What changed

Every contact now gets a lead record.

Why that's cheap: creating a record costs nothing; researching is what costs. So the rest arrive queued and can be run one at a time whenever they're worth it.

Don't limit research to three. Track credits. Make it faster.

What changed

A cap on count became a cap on budget, checked before each contact rather than once at the start.

A reserve is held back so a campaign already under way can finish.

Contacts are researched several at a time, capped at three.

Why capped at all: unlimited concurrency would burn the whole month's search allowance in one campaign.

Measured: four contacts fully researched in 98 seconds, against roughly four minutes one after another. Running out degrades rather than fails — contacts still found, addresses still worked out, only the deep research stops, and the receipt says which.

Choosing the right hook

The longest thread, six attempts, and the one where being wrong repeatedly was itself the useful signal.

It picked the wrong hook for Maheedhar.

Why it mattered

It opened on a work anniversary rather than the company's move to AI agents. Refusing to accept that was the right call.

What changed, in order 
1  undated facts scored 0.35, beating dated ones      → cut to 0.22
2  an undated fact inherited a stale twin's age
3  relevance to what you sell became a multiplier
4  "AI" was being dropped by a 3-letter minimum
5  a third of dates were the run's own date            → distrusted
6  the person-level bonus needed a real category, not "other"
What I got wrong:

All six were adjustments to the same maths, and each produced a different weak hook — an anniversary, then a 2014 exam result, then a former employer.

Four attempts in, the number of attempts was itself the evidence that maths was the wrong tool. Converging would have meant tuning. Jumping around meant the model was wrong.

I should have stopped at two.

Give more weight to posts and reposts, then his current job.

Why it mattered

This was the correction that mattered. Not another weight — an ordering.

What changed 
tier 0   what they said or did themselves
tier 1   their current job, and that company now
tier 2   anything else about them
tier 3   a company that isn't theirs any more

The tier beats the score. Inside a tier the score decides everything; across tiers it gets no vote at all.

Why an ordering works where a score didn't: a score assumes every fact sits on one shared scale. They don't. “He posted last week” and “his old employer won an award” are different kinds of thing, and forcing them onto one number is exactly what let the award win.

Don't exclude anything. Learn to prioritise. Always make a collective call.

Why it mattered

Age was a hard cutoff, which threw away the thing that often says who a person is.

And scoring facts one at a time can't answer “of these eight, which is worth opening with”.

What changed

Age became a penalty that keeps shrinking and never reaches zero.

Why a penalty rather than a cutoff: a cutoff has to name a day when a fact stops mattering, and no such day exists. A decaying penalty says “less useful over time” without ever saying “worthless”.

Career history is kept and handed to the writer as background, fenced off — current employer named, everything else labelled former.

Then the rules narrow it to eight, and one AI call decides among them — or declines, falling back to the ranked order.

Result: it overruled the top-scoring fact and chose “Zamp transitioned completely towards AI agents”, giving as its reason that the shift lines up with what the sender sells. Which is the fact this whole thread had been arguing for.

What changed

Make it learn the weights from what I actually send.

Why it mattered

The default weights are one team's opinion about which signals matter. A recruiter, an investor and a finance vendor want completely different things.

What changed

Only costly actions count. A send is worth double a hand-pick.

A draft you ignored teaches nothing.

Why ignoring must count for nothing: drafts get ignored because the day ended or the lead went cold, not because they were bad. Counting inaction as dislike would teach it that everything is bad, and it would drift back to the defaults.

It only ever promotes, never demotes — absence of evidence isn't evidence.

Learned from your own history: two hand-picked speaking hooks → ×1.2, rising to ×1.4 once campaign sends were counted too. On two facts of equal age the defaults pick the promotion 0.3725 to 0.3353; with learning applied the talk wins 0.4023 to 0.3725 — the order flips.

Where every setting lives, and what it changes

Five tabs behind the persona avatar in the sidebar, or the gear at the bottom. Nothing here is decoration — each field is read at a specific moment, and this is where.

Persona · who's writing, and how

What you fill in

Avatar and name · Character · Who's writing (founder, CEO, CRO, VP, AE, SDR) · What the message is for (book a call, open a relationship, partnership, ask an opinion, re-engage, hiring, event) · What you sell · The problem it removes · Proof · What makes someone worth writing to · Writing instructions.

Where it gets used 
persona → the drafting prompt
        → the campaign template prompt
        → the relevance score when ranking facts

Seniority and purpose aren't labels — each one carries a stance into the prompt. A founder can say “I built this”; an SDR can't. “Ask an opinion” produces a different closing line from “book a call”.

The order in the prompt matters: who's writing → what it's for → what you sell → how you write → what it's learned. Later instructions win, so a learned rule can override the base voice without rewriting it.

Learned · what it's picked up from you

Two lists, two different things

Rules from your edits — how you write. Written down after three consistent edits, corrected rather than stacked up, capped, and versioned so you can undo one.

Signals you act on — what you write about. An accordion: open a row to see the actual hooks in that category.

Why three edits, not one: one edit is a mood. Three is a preference.

Where it gets used 
edit rules → a "learned from their edits" block in the prompt
signals    → a multiplier on the score of matching facts
This is the self-learning claim, made inspectable. Every row shows the evidence behind it, so no multiplier has to be taken on faith.

Sender · the identity messages come from

What you fill in

Your name, role and company · What you sell · The problem it removes · Proof · Goal of the email · Tone. Plus connected services — and the only button in the app that spends an allowance to answer “does this actually work”.

Where it gets used 
sender → the drafting prompt
       → the relevance score
       → the email signature and the reply-to address

Why both Persona and Sender are read: they're filled in at different times — the persona on day one, the sender config later. Reading only one leaves you blind half the time.

ICP · who's worth writing to at all

What you fill in

Target seniority and function · Countries · Industries · Company size · Revenue note.

Where it gets used 
ICP → a 0-100 fit score at the start of every run
    → the priority order on the dashboard and lead list
    → role groups when a campaign needs to find people

Why the score doesn't block anything: it orders the list rather than gating it. A lead is hot on a fresh job change, high on a strong fit plus a personal hook, and lower when only one of those holds. A perfect-fit lead with no angle isn't the one to start with.

Intent · which signals matter to you

What you fill in

Personal signals (promotion, role change, looking for something, speaking, influence, personal award) and company signals (hiring, AI transformation, cost reduction, IPO, expansion, fundraise, product launch, partnership, award).

Where it gets used 
intent weights → the score of every single fact

Why an explicit setting always beats a learned one: a setting is a statement, an inference is a guess.

This is the single field that turns the tool into a recruiter's or an investor's. They need the same mechanism with a different ordering — configuration, not a rebuild.

Not in the app · the environment

Why these aren't settings

The Gmail address and app password, the database address, and the service keys live outside the app and never in the database.

Why: an app password is send access to a real mailbox. Anything the app can write into a database, some future bug can read back out. Putting it behind a form puts it one bug away from being leaked.

What the app does show

Whether each one is configured, and for the ones that report it, how much of the month is left — read from a local count, so asking costs nothing.
