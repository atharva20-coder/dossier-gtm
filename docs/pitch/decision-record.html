Making it usable

The build worked. It did not yet behave like a product someone would open twice.

Make it work on small screens.

Why it mattered

A four-pane layout is four screens on a phone, and an interviewer may open it on one.

What changed

Below 1024px the panes become tabs — chosen in JavaScript, not CSS. Two copies behind hidden lg:* would mount every pane twice, firing every request twice and letting the hidden copy drift out of sync.

Also fixed: h-screen → h-dvh, because mobile browsers count their collapsing address bar in vh and the chat box was sitting underneath it.

Add a dark theme with a switcher.

Why it mattered

Roughly 180 hardcoded hex values meant the app could only ever be light.

What changed

Each shade became a role-named variable — one per shade that existed, not a tidied semantic scale, so light mode renders byte-identical to the design it was matched against. Dark was recomputed rather than inverted: a straight inversion collapses #FAFAFA and #FFFFFF into one flat black and the message stops reading as a card.

Caught in the sweep: ring-offset defaults to white — a bright halo around the selected persona on a dark rail — and text-white on ink-filled buttons had to flip while the same class on blue and green buttons had to stay.

The persona modal only opens on the second click.

Why it mattered

You reported it twice. The code was already correct, which meant the bug was somewhere else.

What changed

The server sent no Cache-Control on index.html, so browsers cached it heuristically and kept loading a bundle that had been replaced.

The same class of bug returned later and cost more: API responses had no cache header either, so a run re-read straight after the assistant rewrote it came back as the copy from before the rewrite. Now no-store on everything under /api/.

Rebuild the dashboard like this reference.

Why it mattered

It was a table. The question a rep asks is "who do I work today", which a table does not answer.

What changed

Stat tiles, an area chart, stacked bars, ranked categories, avatars. Hand-drawn SVG rather than a chart library — three forms of a few dozen lines each against ~180KB of runtime and a second dependency to keep in step with the theme.

Colour was computed, not chosen. The palette was run through a validator: ordinal ramp, one hue, monotone lightness, pale end clearing the surface at 2.11:1 light and 2.25:1 dark. Outcomes use an ordinal ramp rather than categorical hues because the three outcomes are ranked, not merely different.

Letting it send

The one action that reaches a real person and cannot be undone.

Add a real send button. Use Gmail and an app password.

Why it mattered

A tool that drafts but cannot send is a demo. A tool that can send carelessly is a liability.

What changed

SMTP over STARTTLS in a thread, so a blocking socket cannot stall the event loop. Every guard lives in one function so the rules cannot differ by screen: blocked relationship, unparseable address, empty draft, already-sent-without-confirmation.

Login became the mailbox. Signing in with the sending account's own credential means whoever is signed in is demonstrably the person the messages come from — compared in constant time on both halves so the address is not enumerable.

Send one to this address.

Why it mattered

Nothing had ever actually been sent. Everything up to that point was theory.

What changed

One real message, through the production path, to the address you named. The resend guard then refused a second attempt with "Already sent… Confirm again to send another."

Proved on a real record, not a mock: credential, SMTP path, sent indicator, and the guard all worked. reset_run deliberately does not clear that record — re-running research must never erase the fact that someone was emailed.

No campaign should be able to mail everyone.

Why it mattered

A campaign that can mail forty strangers from one button is a different product with a different blast radius.

What changed

One contact per request, everywhere. There is no bulk send and the interface says so under the button.

Living on free tiers

Every provider optional, every allowance visible, nothing spent by accident.

The app must work if keys are missing or expired.

Why it mattered

Free tiers run out, usually on the day you need them.

What changed

Absent, wrong and out-of-quota now behave identically — the run completes, only the reason differs. Verified by running the whole pipeline with three keys deliberately set to garbage.

Two real problems found doing it: no HTTP timeouts anywhere — aiohttp defaults to five minutes, so one unreachable host would have stalled a forty-contact campaign for hours. And an expired key was reported as "no match", which is the one message that stops someone fixing it.

Apollo is paid. Not using it. PDL either.

Why it mattered

The plan assumed Apollo's api_search was credit-free. It is not.

What changed

Both removed entirely rather than left behind a key. A paid dependency for something the free path already does is not a fallback, it is a branch that never executes — every run in the repo had gone through the search path anyway.

All the APIs are free and limited. Never spend on a page load.

Why it mattered

This was worse than it looked.

What changed

/api/health was making a real Tavily search and a real Gemini call, cached five minutes. A tab left open all day was spending search credits to draw a status badge. It now answers from configuration alone; a single "Check now" button in Setup is the only thing that spends.

Measured: four page loads → zero provider calls. The app also counts its own Tavily searches, because Tavily exposes no endpoint to ask what is left, and warns before a campaign dies halfway.

Here is a Hunter key.

Why it mattered

Testing it against the live API immediately exposed a bug in how it was read.

What changed

Hunter returns status nested under verification, not at the top level. The code read the top level, so it was always None — Hunter's own "valid" was discarded, the paid credit wasted, and a correct verified address fell through to a calculated guess.

And the verifier caught a fabricated address: QuickEmailVerification returns "valid" for an invented mailbox at an accept-all domain. Trusting it would have certified a made-up address as confirmed. Verification now also requires safe_to_send and not accept_all — and every field arrives as the string "true"/"false", where bool("false") is True.

Campaign contacts should be treated like leads.

Why it mattered

Only the first three became leads. The rest existed solely inside the campaign and could not be opened or re-researched.

What changed

Every contact gets a lead row. Creating one is free; researching is what costs, so the rest arrive queued and can be run individually whenever they are worth it.

Don't limit research to three. Track credits. Make it faster.

What changed

The count-based cap became a budget-based one, checked before each contact rather than once at the start, with a reserve held back so a campaign already under way can finish. Contacts research concurrently, bounded at three.

Measured: four contacts fully researched in 98 seconds against roughly four minutes in series. Running out degrades rather than fails — contacts still found, addresses still worked out, only the deep research stops, and the receipt says which.

The persona should always write the drafts.

Why it mattered

The opener used the full persona brief. The template — the larger half of every message — reduced it to name and character, dropping the writing instructions, the seniority stance and every learned rule.

What changed

Both halves now use the same brief. A persona whose instruction says three sentences, direct, engineer-to-peer previously produced five corporate ones.

Choosing the right hook

The longest thread, six attempts, and the one where being wrong repeatedly was the useful signal.

It picked the wrong hook for Maheedhar.

Why it mattered

It opened on a work anniversary rather than the company's move to AI agents — and refusing to accept that was right.

What changed, in order 
1  undated facts scored 0.35, beating dated ones → 0.22
2  an undated fact inherits a stale twin's age
3  relevance to what you sell became a multiplier
4  "AI" was being dropped by a 3-character token floor
5  a third of dates were the run's own date — distrusted
6  the person-tier boost required a real trigger, not "other"
What I got wrong: all six of those were multiplier tuning, and each produced a different weak hook — anniversary, then a 2014 exam result, then a former employer. Four attempts in, the number of attempts was itself the evidence that arithmetic was the wrong instrument. I should have stopped at two.

Give more weight to posts and reposts, then his current job.

Why it mattered

This was the correction. Not another weight — an ordering.

What changed 
band 0   what they said or did themselves
band 1   their current job, and that company now
band 2   anything else about them
band 3   a company that is not theirs any more

Bands beat scores. Within a band the score decides everything; across bands it gets no vote — so no amount of corroboration lets a former employer outrank a post from last week.

Don't exclude anything. Learn to prioritise. Always make a collective call.

Why it mattered

Age was a hard gate, which threw away the only thing that often says who a person is. And scoring facts one at a time cannot answer "of these eight, which is worth opening with".

What changed

Age became a penalty that keeps falling and never reaches zero. Career history is kept and passed to the drafter as background, fenced off, with the current employer named and the rest labelled former. Then the rules narrow to a shortlist of eight and one judgment decides among them — or declines, falling back to the ranked order.

Result: it overrode the arithmetic's top choice and picked "Zamp transitioned completely towards AI agents", giving as its reason that the shift aligns with what the sender sells. The fact this whole thread had been arguing for.

A VP at one company ten years ago, now an SVP elsewhere — that matters.

Why it mattered

Three separate reasons, and the third is a correctness bug: they changed company, they are more senior now, and qualifying them against the wrong company is simply wrong information.

What changed

Career history is no longer discarded. drop_wrong_company was deleting it outright — any fact whose subject company differed, including a person-level fact about the prospect at a former employer — so the case you named never survived extraction.

Verified end to end: given Adobe and Oracle as history and Ramp as current, the draft names Ramp and neither of the others.

Make it learn the weights from what I actually send.

Why it mattered

The weight table is one team's opinion about which triggers matter. A recruiter, an investor and an AP vendor want different things.

What changed

Only costly acts count. A send is worth double; hand-picking a hook counts; a draft left alone teaches nothing, because not acting is not a preference and counting it would just re-learn the defaults. Promotion only — it never demotes on absence of evidence.

Learned from your own history: two hand-picked speaking hooks → ×1.2, rising to ×1.4 once campaign sends were counted too. On two facts of equal age the taxonomy picks the promotion 0.3725 to 0.3353; with learning applied the talk wins 0.4023 to 0.3725.

Where every setting lives, and what it changes

Five tabs behind the persona avatar in the rail, or the gear at the bottom of it. Nothing here is decoration — each field is read at a specific point in the pipeline, and this is where.

Persona · who is writing, and how

Fields

Avatar and name · Character · Who is writing (founder, CEO, CRO, VP, AE, SDR) · What the message is for (book a call, open a relationship, partnership, ask a perspective, re-engage, hiring, event) · What they sell · The problem it removes · Proof · What makes someone worth writing to · Writing instructions.

Where it is read 
persona → draft._persona_block() → the drafting prompt
                                  → the campaign template prompt
       → judge.offer_terms()      → the relevance multiplier

Seniority and intent are not labels — each carries a stance into the prompt. A founder may say "I built this"; an SDR may not. "Ask a perspective" produces a different ask from "book a call".

The order in the prompt is load-bearing: who is writing → what it is for → what they sell → how they write → what has been learned. Later instructions win, so a learned rule can override the base voice without rewriting it.

Learned · what it has picked up from you

Two lists, two different things

Rules from your edits — how you write. Inferred after three consistent edits, corrected rather than piled up, capped, and versioned so you can undo one.

Triggers you act on — what you write about. An accordion: open a row to see the actual hooks in that category. A send counts double a hand-pick; a draft you left alone counts nothing.

Where it is read 
memories → the LEARNED FROM THEIR EDITS block in the prompt
triggers → judge.learned_weights() → intent weight multiplier
This is the self-learning claim, made inspectable. Every row shows its evidence, so the multiplier is never a number to take on faith.

Sender · the identity messages come from

Fields

Your name, role and company · What you sell · The problem it removes · Proof · Goal of the email · Tone. Plus Connected services and the only button in the app that spends an allowance to answer "does this work".

Where it is read 
writer → draft._writer_block()   → the drafting prompt
       → judge.offer_terms()     → relevance
       → the email signature and the Reply-To

Persona and Sender are both read because they are filled in at different times — the persona on day one, the sender config later — and reading only one is blind half the time.

ICP · who is worth writing to at all

Fields

Target seniority and function · Geographies · Industries · Headcount range · Revenue note.

Where it is read 
icp → profile stage → icp_score (0-100)
                    → priority band on the dashboard and the lead list
    → contacts.find() when a campaign needs role groups

The score does not block a run. It orders the list: a lead is hot on a fresh job change, high on a strong ICP score with a person-level hook, and lower when only one of those holds. A perfect-fit lead with no angle is not the one to start with.

Intent · which triggers matter to you

Fields

Person-level intents (promotion, role change, looking for, speaking, influencer, personal award) and company-level ones (hiring, AI transformation, cost reduction, IPO, expansion, fundraise, product launch, partnership, award).

Where it is read 
intent_weights → judge.intent_weight() → the score of every fact

An explicit weight here always beats the learned one — a setting is a statement, an inference is a guess. This is the single field that turns the tool into a recruiter's or an investor's: they need the same mechanic with a different ordering, which is configuration rather than a rebuild.

Not in the interface · the environment

Why these are not settings

The Gmail address and app password, the database URL, and the provider keys live in the environment and never in the database. An app password is mail-send access to a real mailbox; putting it behind a form in the app is putting it one bug away from being read back.

What the app does show

Whether each is configured, and for the ones that report it, how much of the month is left — read from a local count so asking costs nothing.
