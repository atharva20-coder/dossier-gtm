Four Runs to Rehearse

One that works and three that go wrong on purpose. Each has the exact input, what appears on screen, and what to say while it runs. Every output below is copied from a real run.

Run them in this order. Each one answers the question the previous one leaves hanging.

  1. It works — a lead already finished, open before you start talking
  2. Two people share a name → it stops and asks
  3. Nothing real to say → it refuses to invent something
  4. Every key is broken → it finishes anyway

Why that order. Run 1 buys credibility. Run 2 shows judgment. Run 3 shows honesty. Run 4 shows it survives the real world. Do 3 before 2 and “it refuses to guess” lands with nothing behind it.

1 · It works

open this before you speak
Input · already finished, so nothing loads live

Maheedhar Maram · Zamp · Founder's Office linkedin.com/in/maheedhar167

Say, before you click anything

“This one's already run, so you're seeing the finished state — I'll run a live one in a minute. Fifty-eight pages read, thirty-nine of them about him rather than about Zamp.”

Point at these, in this order 
1. the hook, and its source link      → click it, land on the real page
2. the findings column                → "everything it looked at, kept or dropped"
3. the research map button            → how it got there, step by step
4. untick a fact → Rewrite            → the email rebuilds from what is left
5. a tone chip (Shorter)              → same facts, different style
Say

“Forty minutes of a rep's research, in about a minute. But the number I care about is the second one — every claim in that email traces back to a page I can open.”

Why start here rather than with a live run

Because the first thirty seconds decide whether they're watching the tool or watching a loading bar. A finished run puts the reasoning on screen immediately. The live runs afterwards prove it wasn't staged — so you get both, in the right order.

2 · Two people share a name

run this live
Input · type exactly this, and leave company blank

Name: Michael Chen Company: (leave empty) Role: (leave empty)

Say, before running

“The most expensive mistake this can make isn't a clumsy sentence. It's researching the wrong person and then emailing a real one about them. So here's a name given deliberately with no company.”

What actually comes back 
status: needs_disambiguation
identity: 4 believable matches — waiting for you to confirm

  Adventist Healthcare  · Interventional Cardiologist
  Akin Gump             · Associate, Disputes & Investigations
  (no company)          · Actor
  (no company)          · Director of Operations
Say, pointing at the four

“It found four real people and stopped. It hasn't spent a search budget and it hasn't guessed. It waits here until someone picks — and picking is cheap, it carries on rather than starting over.”

Why it stops instead of picking the likeliest

Because the two outcomes cost wildly different amounts. Guessing right saves four seconds. Guessing wrong produces a beautifully researched email about a stranger, sent under a real name, to someone who spots it instantly. No confidence percentage captures that gap — so it has to be a rule, not a threshold.

If they push: “doesn't that jam a batch of 200?”

Only the unclear ones stop; the rest finish. And it's rare — give it a company name and identity resolves instantly at 100%, with no interruption at all.

3 · Nothing real to say

run this live
Input · a real-sounding person with no public footprint

Name: Harshad Vaidya Company: Kelphi Systems Role: Operations Lead

Say, before running

“Every tool in this space will happily write you a personalised email about anyone. That's the problem — the AI will invent a funding round without blinking. Watch what this one does when there's genuinely nothing there.”

What actually comes back 
research  44 pages read — 21 about a person, 23 about a company
extract   1 possible fact; 15 facts about someone with the same
          name thrown out — no source tied them to Kelphi Systems
judge     nothing cleared the bar
draft     No specific public signal was found — this is a
          deliberately generic draft, labelled as such

status: no_signal_found
Say — the strongest moment in the whole demo

“It read forty-four pages, found fifteen facts about a different Harshad Vaidya, and threw away every one because nothing tied that person to this company.”

“Then it wrote a generic message and labelled it generic. It would rather hand you an honest blank than a convincing lie. That's the entire design in one screen.”

Why label it rather than just fail

Because a rep sometimes still wants to send something, and a hard failure just sends them off to write it themselves with less information. Labelling leaves the choice with the person while making sure their own tool can't mislead them. Same principle as showing sources, applied to the absence of any.

run status: completed
Say

“It finished. The address was worked out from the company's naming pattern rather than looked up, and it says so — on screen, and in the CSV a sequencer would import.”

“Three services failed and the run didn't. The only thing that changed is the reason it gives you.”

Why this run earns its demo time

Because it proves the tool survives contact with reality rather than a rehearsed happy path. It also came out of a real bug: an expired key was originally reported as “no match” — the one wording that stops someone fixing it. Breaking the keys deliberately is how I found that.

Restart afterwards

Kill that server and start a normal one before anything else, or every demo after this runs degraded and you'll explain it twice.

Held in reserve — don't run unless asked

Four is already a lot for one call. These are worth mentioning if a question opens the door.

  • A colleague's fact, dropped. On a normal run the extract line reads “1 fact about a different person at the company discarded”. It fires by itself — point at it if you see it rather than staging it.
  • Only old facts exist. It picks the best of what's left, up to two years back, and says plainly: “nothing recent cleared the bar… read it before sending.”
  • An address that would bounce. A worked-out address that fails verification is cleared rather than shipped, with the reason “looks like a typo for …”.

Two things to do an hour before

  • Run each of the four once. Live search results shift. The four Michael Chens may not be the same four next week — the behaviour will hold, the names may not. Don't quote them from memory.
  • Have run 1 already open in a tab. Never let an interviewer watch a loading spinner in the first thirty seconds.

If something breaks live

  • Say what happened, and read the message off the screen.
  • A tool that reports its own failure clearly is the exact point you've been making for twenty minutes.
  • Don't apologise for it. Use it.

Every edge case here is something that broke first and then got a guard. That's the honest answer to “how did you choose these” — they chose themselves.
